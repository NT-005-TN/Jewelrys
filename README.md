# Jewelry Workshop API

Java 17 · Spring Boot 3.5.16 · PostgreSQL · Redis.

## Запуск

1. Скопируйте `.env.example` в `.env`.
2. Задайте новый `DB_PASSWORD` и `APP_JWT_SECRET` (Base64 от минимум 64 случайных байтов).
   Пример генерации ключа: `python -c "import secrets,base64; print(base64.b64encode(secrets.token_bytes(64)).decode())"`.
3. Задайте `MAIL_USERNAME`, `MAIL_PASSWORD` и `PUBLIC_BASE_URL` — публичный адрес API,
   включая `/api`, без завершающего слеша. Для локальной разработки: `http://localhost:8080/api`.
4. Запустите Docker Engine, затем `docker compose up --build`.
5. Swagger: http://localhost:8080/api/swagger-ui.html. Health: http://localhost:8080/api/actuator/health.

Для первого администратора установите `SPRING_PROFILES_ACTIVE=init-admin`, `ADMIN_EMAIL`,
`ADMIN_PASSWORD` (не менее 12 символов). После создания верните профиль `default` и
пересоздайте контейнер приложения. Существующая учётная запись не перезаписывается.

`.env` автоматически используется Compose, но не `bootRun`: при локальном запуске
передавайте переменные окружения явно. Пароль существующего тома PostgreSQL не меняется
от редактирования `.env`. Не удаляйте рабочий том для смены пароля.

Ранее опубликованные SMTP/JWT/DB/admin секреты необходимо отозвать и заменить;
удаление из текущих файлов не удаляет их из истории Git.

## Проверки

```text
gradlew.bat test bootJar --no-daemon
gradlew.bat integrationTest --no-daemon
```

На Linux/macOS используйте `bash gradlew`. `integrationTest` требует Docker и запускает
изолированные PostgreSQL 15/Redis 7 через Testcontainers. В CI запускаются обе группы.
Для отдельной локальной тестовой PostgreSQL можно задать `TEST_DATABASE_URL`, например
`jdbc:postgresql://127.0.0.1:55432/postgres` (пользователь `workshop_test`, пустой пароль).
В этом режиме тест настоящего Redis явно пропускается. Используйте только одноразовую БД:
тесты создают пользователей, заказы и товары. Локальные результаты см. `TECH_DEBT.txt`.

## Аутентификация

Пути имеют префикс `/api/auth`:

| Метод | Путь | Данные |
|---|---|---|
| POST | `/register` | RegisterRequestDTO, password, confirmPassword |
| POST | `/login` | email, password |
| GET | `/verify-email` | token в query |
| POST | `/refresh` | refreshToken |
| POST | `/logout` | refreshToken |
| POST | `/forgot-password` | email |
| POST | `/reset-password` | token, newPassword |
| GET | `/reset-password-form` | страница из ссылки в письме |

Защищённые запросы: `Authorization: Bearer <accessToken>`. Одна активная сессия на
пользователя: новый вход отзывает предыдущую. Subject JWT — стабильный userId; version
проверяется по БД. Выход, смена пароля, блокировка и смена роли отзывают access/refresh
для последующих запросов. Уже выполняющийся запрос принудительно не прерывается.
Refresh хранится только как SHA-256-хеш; ротация и проверка выполняются под блокировкой
пользователя в одной транзакции. Повторный refresh с прежним токеном отклоняется.
Старые JWT предыдущих версий приложения несовместимы — после обновления нужен вход.

## Заказы и отчёты

Остатки изменяются под блокировкой товара, товары блокируются по возрастанию ID.
Отмена блокирует заказ и возвращает товар один раз; повторная отмена — без изменений.
Ручная правка остатка задаёт абсолютное значение и использует ту же блокировку.

Переходы: PENDING → PROCESSING/COMPLETED/CANCELLED;
PROCESSING → COMPLETED/CANCELLED; COMPLETED → DELIVERED/CANCELLED;
DELIVERED → CANCELLED (возврат); CANCELLED — конечный статус.
Клиент может отменить только PENDING/PROCESSING. Повторный тот же статус идемпотентен.
История заказов сохраняется при смене роли пользователя.

Выручка учитывает только COMPLETED/DELIVERED, по дате создания заказа. CANCELLED,
включая возвраты, исключается. Интервал start/end включительный; даты отчётов — UTC.
Карточки товаров отражают сумму позиций до скидки заказа; итоговая выручка — после скидки.
LTV считается за всё время; новые клиенты и лидеры — за запрошенный период.
Отчёт по товарам ограничен 100 строками. Для больших выгрузок нужен отдельный экспорт.
HTTP page >= 0, size от 1 до 100; days от 1 до 3660.

## Почта, аудит и эксплуатация

Письма записываются в `email_outbox` вместе с бизнес-транзакцией. Фоновая доставка
использует `FOR UPDATE SKIP LOCKED`, таймауты SMTP, до 10 попыток с увеличением задержки.
После успеха тело с одноразовыми ссылками очищается. Доставка at-least-once: при сбое
между отправкой SMTP и фиксацией БД возможно повторное письмо. Для строк с attempts=10
нужно проверить SMTP и вручную разрешить повторную попытку после устранения причины.
Доступ к таблице ограничьте: неотправленные письма содержат одноразовые ссылки.

PUBLIC_BASE_URL используется для подтверждения и формы сброса. Токен сброса находится
во fragment ссылки и удаляется из адресной строки страницы; пароль отправляется JSON POST.
На публичном сервере используйте HTTPS. Настройки SMTP по умолчанию Gmail; для другого
провайдера передайте SPRING_MAIL_HOST/PORT в окружение приложения.

Миграция V4 добавляет сессии и outbox, V5 — транзакционный аудит users/clients/products/
orders/materials. Аудит исключает пароли и токены; для фоновых/анонимных действий actor
пустой (system). До обновления сделайте резервную копию рабочей БД. V1–V3 не изменены.

X-Request-ID связывает ответ с логами. Health открыт, остальные actuator endpoints
требуют аутентификации. Redis используется для атомарных лимитов запросов; недоступность
Redis не обходится молча. Не доверяем входящим X-Forwarded-For/X-Real-IP: за reverse proxy
необходимо отдельно настроить доверенные прокси и очистку forwarded-заголовков.

Dependabot и dependency review добавлены в `.github`; они начнут работать после
публикации в GitHub. Их конфигурация не означает, что удалённый CI уже прошёл.
